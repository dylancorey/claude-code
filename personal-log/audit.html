Ledger Audit Register

Twenty-three findings against the live artifact, ranked, with an execution spec for the agent that fixes them.

Artifact 7b605c39 Version read 1788304833-dea8 Source 2,474 lines, read in full Entries 9 Catalog 18 Date 2026-09-04

The architecture is better than the product. The persistence layer, the self-rebuilding document, and the theme system are genuinely well built — better than most artifacts of this size, and they should not be touched. What's weak is everything that decides what a memory is worth: there is no rating, no capture timestamp, and no undo. The ledger records that you went somewhere. It cannot record whether it was any good.

Three findings are live data bugs, not design opinions: a malformed home-base string that permanently mislabels two neighborhoods, a fabricated street address shipped in the Discovery catalog, and a sort order that files every undated entry at the bottom of the page under "Someday" — where three of your nine entries currently sit.

Nothing here was implemented. Six questions in §11 need answers before Phase 1 starts.

§ 01

What already works and should be preserved

These are load-bearing. The execution spec in Stage 2 forbids touching them without explicit approval.

01
Self-publishing persistence L2444–2468

persist() calls window.claude.use('artifact') and republishes the whole document. Entries survive browsers, devices and sessions — this is real durability, not localStorage. The error taxonomy is unusually complete: it distinguishes conflict, rate_limited, too_large and six separate permission codes, and flips the page to readOnly rather than pretending a save worked.

02
The document rebuilds itself L2422–2440

buildDocument() reconstructs the page from its own <style> and <script> text plus fresh JSON. The < → \u003c escape correctly prevents a note containing </script> from destroying the file. This is the mechanism that lets both you and Claude edit the same ledger. Preserve exactly.

03
Three-state theming L17–88, L1111–1144

Tokens are defined on bare :root, redefined under prefers-color-scheme guarded by :not([data-theme="light"]), and again under [data-theme="dark"]. A MutationObserver re-applies the choice when the host restamps the root. This is the correct pattern and most pages get it wrong.

04
Category-driven schema L1026–1071

CATS drives form fields, summary lines, per-category statuses and the title label from one object. Adding a category is a data change, not a code change — which is exactly how place got added. Extend this; don't route around it.

05
Personality as data L1075–1102

LINES keys every piece of voice copy by tone. Nothing is hardcoded in a render function. The salty variants are genuinely funny and never aimed at you — "You filtered so hard you filtered out your own life" is the correct register for this product.

06
Escaping discipline L1189–1193

esc() is applied at every single interpolation into innerHTML. I checked all of them. Given the page renders user notes and Claude-authored catalog text into markup, this is what stops a stray apostrophe or angle bracket from breaking the ledger.

07
Motion restraint L507–509, L1913

prefers-reduced-motion is honoured in CSS and the spin reel checks matchMedia and skips straight to the result instead of animating a 2.5s transform. That second check is the one people forget.

08
The empty states L1511–1515

Two distinct empties — nothing logged yet vs. nothing matches your filters — each tone-aware, each offering the right next action. Most products ship one generic "No results." Keep both.

§ 02

Current product model and primary journeys

The model. One self-contained HTML document. All state lives in a single JSON block (#entry-data, L515–1002) inside the page itself. Every mutation rewrites the entire document and publishes a new artifact version, so version history is the undo stack — except nothing in the UI exposes it. Claude is a co-equal editor through the same URL. Four categories (food, screen, live, place), three statuses (logged, watching, wishlist), free-text tags, one comma-separated home-base string that drives "Away" marking, and an 18-item Discovery catalog that Claude stocks by hand because the page is sandboxed from the network.

The entry shape is {id, category, status, title, date, fields, with, tags, note}. Note what is absent: no rating, no created/updated timestamp, no cost, no photo, no revisit count. date is the date of the event, not of the record — a distinction that causes three separate findings below.

J1
Capture
Add entry → pick category → pick status → title → date → 3–5 fields → tags → note → Add to ledger → republish

Roughly eight interactions and a full document publish for "I ate at Sonny's." This is the journey you run most and it is the slowest thing in the product.

J2
Retrieve
sticky bar → search / category stat / status pill / tag chips → cards grouped by year → open detail

Filters are session-only and produce no URL. You cannot bookmark or return to a view.

J3
Decide
Spin it (random wishlist) · Suggest something (ranked + observations) · Order again (flagged dishes)

Three separate tools for one question — "what should I do tonight?" — presented as three identical pills.

J4
Discover
Discover → query → scope + Near → ranked catalog → Save to ledger → prefilled review form → republish

The review-before-save step is the right design. The index behind it is 18 items and cannot grow without asking Claude.

J5
Reflect
On This Day banner · Year in review → tiles, tag bars, people, months, first/last, cities

The strongest part of the product conceptually, and the part most damaged by missing data (see F03, F19).

J6
Configure
gear → voice (plain / dry / salty) + home base · theme segment in header

Home base is a single free-text string with no validation. It is currently malformed (F06).

§ 03

The most serious problems

Twenty-three findings, ordered by severity. Impact/effort is scored 1–5. Everything cites the live source.

F01
No rating. The ledger cannot record whether anything was good. Critical I 5 · E 2

CATS L1026–1071 · recommend() L1329–1378 — Not one category has a quality field. You can record that you ate at Open Sesame; you cannot record that it was worth returning to. This is the single largest gap in a product whose stated job is memory.

It cascades: recommend() scores wishlist items on tag overlap, city repetition, cuisine repetition and category recency — every signal except whether you liked the comparable things. "You keep ending up around Hollywood" is offered as a reason to go somewhere, with no idea whether Hollywood has been good to you.

Fix

Add an optional rating (1–5) plus a boolean again ("would repeat") to the entry root, not to fields — it is cross-category. Render as a five-dot control in the form and a compact glyph on the card. Weight recommend() by it. Leave it null for existing entries and never infer a value.

F02
Delete is immediate, permanent, and one click from the entry you were reading. Critical I 5 · E 2

L1761–1764 — delete-confirm filters the entry out of state.entries and calls persist() in the same tick. There is a two-step confirm, which helps, but no trash, no undo and no in-product path back. Recovery means asking Claude to dig through artifact version history and hand-restore JSON.

For a ledger meant to accumulate for years, an irreversible delete on a mis-tap is the highest-consequence failure in the product.

Fix

Soft delete. Move to a trash array with deletedAt; show "Deleted — Undo" for 10s in a live region; add a Trash view in Settings that restores or purges. Purge is the only place a hard delete lives, behind its own confirm.

F03
"Newest" files just-added entries at the very bottom, under "Someday". Critical I 5 · E 2

compare() L1424–1432 · yearOf() L1208 — Sorting is by event date. Undated entries return 1 from compare(), so they sink below everything, and yearOf() buckets them into a group literally titled "Someday" at the end of the page.

Add a film you want to watch and it does not appear at the top under "Newest" — it appears last, past every dated entry, below the fold. Three of your nine live entries are there right now: Dune: Part Two, Anora, The Meg. This is why the ledger feels like it swallows things.

Fix

Depends on F04. Once entries carry createdAt, "Newest" sorts on date || createdAt. Separately, promote undated wishlist items to a pinned "Someday" group at the top when the status filter is Want-to, and rename the sort options to "Recent", "Oldest", "A–Z" so the label stops overpromising.

F04
No entry has a creation or modification timestamp. Critical I 5 · E 2

entry shape L833+ · newId() L1181 — The record knows when the event happened and nothing about when you wrote it down. So: no "recently added" sort, no "you edited this three times" signal, no way to detect a bad bulk edit, and no ordering at all for the entries you never dated.

newId() embeds Date.now().toString(36), so creation time is technically recoverable from the id for entries created in-app — but not for the two seeded ones (s4, s6), and nothing reads it.

Fix

Add createdAt and updatedAt ISO strings, set on write. Backfill createdAt from the newId() timestamp where parseable, leave null otherwise, and never fabricate one. This is the dependency for F03 and for any history view.

F05
Your home base string is malformed and permanently mislabels two neighborhoods. Critical I 4 · E 1

L519 · homeTerms() L1231–1233 · isAway() L1235–1243 — The stored value ends …Larchmont, Melrose Century City. Two neighborhood names, no comma between them, so they parse as the single term melrose century city. isAway() tests hay.indexOf(term) against the entry's city — no city string will ever contain that phrase.

Result: anything you log in Melrose or Century City is flagged "Away" forever, and the Away tile in Year in Review counts it as travel. There is also a stray double comma after Beverly Hills; that one is harmless because the empty term is filtered out, but it is the same missing validation.

Fix

Two parts. Data: repair the string to …, Larchmont, Melrose, Century City. Product: make home base a chip editor rather than raw text — comma-splits on entry, shows each term as a removable chip, and warns on a term over ~24 characters. That is what would have caught this.

F06
A fabricated street address is shipping in the Discovery catalog. Critical I 4 · E 1

L746 — Granville Studio City carries "address": "12345 Ventura Blvd, Studio City, CA". That is placeholder digits, not a real address, and it feeds a live Google Maps link that will route you to the wrong block. The Broad (L799) and Getty Center (L817) ship address: "", which is at least honest.

This violates the feature's own documented contract — the how-to panel at L2414 states "Use only facts that are actually in the source; leave a field out rather than guessing." The one place that rule was broken is the one place it does visible damage.

Fix

Blank the fabricated address now; the card already degrades correctly to "No street address in this source." Then add a verifiedAt per catalog item and surface unverified ones with a quiet marker, so the index cannot silently drift from its sources again.

F07
Secondary text fails WCAG AA everywhere it appears. High I 4 · E 1

--ink-3 L24 / L55 — Light theme #8B8B94 on white measures 3.38:1. AA requires 4.5:1 for text under 18.66px bold / 24px regular, and every use is 12–13px. Dark theme #757680 on #17181C is ≈4.0:1 and also fails.

That token carries the entire metadata layer: card meta and dates, fact labels, form labels, mini tags, Discovery meta and source attribution, review tile captions, bar values, section counts. Separately, .chip-cat (L266) renders category color on a 13% tint of itself — #D2600B on near-white is ≈3.88:1 at 11px bold.

Fix

Darken --ink-3 to ≥4.5:1 in both themes (light ≈#6B717A, dark ≈#8E959F) and raise --tint or darken the category hues until chip text clears 4.5:1. One token change, entire app fixed. Verify with a contrast check, not by eye.

F08
Save status is invisible to screen readers and parked in the tag bar. High I 4 · E 1

L1584–1587 — save.text renders as a plain <span class="head"> with no role="status" and no aria-live. Saving is the critical path of the entire product, and a screen reader user gets no announcement that a save started, succeeded, or failed.

Visually it is also in the wrong place — bottom-right of the filter bar, same 12px grey as the word "Tags", so a failed save reads as chrome. And "Saved" never clears; it sits there until something else re-renders.

Fix

Move to a dedicated status region with role="status" aria-live="polite" (assertive for failures). Give the three states distinct form, not just color: in-flight spinner, transient success that self-clears after ~2s, persistent error with a Retry button.

F09
Switching category in the form leaves orphaned data that search can still match. High I 3 · E 2

L1845–1849 · collect() L1834–1842 · haystack() L1269–1273 — Changing category calls collect() first, which writes the old category's field keys into draft.fields. Those keys are never pruned. Live evidence: Pampas Grill (food) carries kind, venue and support; The Meg (screen) carries city, cuisine, address and dish.

Today they are all empty strings, so it is invisible. Fill a restaurant's cuisine, switch it to Movies, save — the cuisine persists in the record, is displayed nowhere, and haystack() still indexes it. The entry matches a search term that appears nowhere on the card or in the detail view.

Fix

On category change, keep keys the new category declares plus any shared key (city, address), and drop the rest — after asking once if a dropped key has a non-empty value. Never discard typed content silently.

F10
Every keystroke in search rebuilds the entire page. High I 3 · E 3

wire() L1620–1633 · render() L1467–1527 · tagCounts() L1443–1452 — The input handler sets ui.q and calls render(), which replaces app.innerHTML wholesale, then re-finds the input, refocuses it and restores the caret with setSelectionRange. That restoration dance exists because the architecture destroys the field the user is typing into.

Each keystroke also re-runs tagCounts(), which walks every entry × every tag. At nine entries this is imperceptible. At several hundred — which is the point of a ledger — it will lag visibly, and the caret restoration will start dropping characters on slower devices.

Fix

Keep the controls bar out of the re-rendered subtree and repaint only the results region; debounce the filter at ~120ms. Delete the focus/caret restoration once the input is no longer destroyed — it becomes dead code.

F11
Toggling category or status in the form throws focus back to the title field. High I 3 · E 2

paint() L1779–1820 · L1818–1819 · handlers L1845, L1850 — Every category and status toggle rebuilds dlg.innerHTML and then unconditionally focuses the title input. Values survive because collect() runs first, but keyboard position does not.

Tab to Status, press a status, and you are teleported to the top of the form. There is no way to complete this form on a keyboard without repeatedly re-traversing it. <dialog> gives correct focus trapping and Esc handling for free — the bug is entirely self-inflicted by the repaint.

Fix

Focus the title only on first paint. On subsequent repaints, restore focus to the control that triggered it via its data-x/data-cat identity. Better: mutate the affected segment in place rather than rebuilding the dialog.

F12
No export. There is no way to get your data out. High I 4 · E 2

whole app — Years of personal history live in one artifact version with no download, no JSON copy, no CSV, no print view. If the artifact is lost, corrupted by a bad publish, or the capability is revoked, there is no local copy and no migration path anywhere else.

Note the sandbox constraint: viewers cannot start a download — <a download> and script-driven saves are inert. So the honest options are a copy-to-clipboard of the full JSON, or the downloads runtime capability if it is available to this account.

Fix

Ship "Copy ledger JSON" in Settings immediately — one button, works today, zero dependencies. Then investigate the downloads capability for a real .json and .csv file. Add a matching paste-to-import behind a confirm that shows what will change.

F13
Discovery search requires every word to match. High I 3 · E 2

discSearch() L2073–2096 — The term loop returns early if any single word is missing from the haystack. So "batman" works, "batman nolan" works, and "good batman movie" returns nothing at all — falling through to the "Nothing indexed" panel even though ten Batman films are sitting in the index.

On an 18-item catalog, strict AND semantics means most natural phrasing dead-ends. The empty state is well designed, which makes it worse: it confidently tells you nothing is indexed when plenty is.

Fix

Require at least one term, score by how many match, and rank multi-term matches above single. Keep the exact-title bonus. Show "Nothing indexed" only when zero terms hit anything.

F14
The sticky control bar consumes most of a phone screen. High I 3 · E 2

.controls L189–193 · breakpoint L501–506 — The bar is position: sticky and holds search, up to three status pills, a sort select, the Add button and the entire tag bar. At 390px that wraps to four or five rows and stays pinned, leaving a narrow slot for actual entries.

There is one breakpoint in the stylesheet, at 46rem. Tablet gets no treatment: .grid at minmax(18.5rem, 1fr) yields two columns on a 768px viewport with a lot of dead gutter.

Fix

Below 46rem, keep only search plus a filter button in the sticky bar and move status, sort and tags into a sheet that opens from it, with a count badge when filters are active. Add a 48–64rem tier so tablet gets three columns.

F15
Discovery's "Near" is a flat bonus with no notion of distance. Medium I 3 · E 3

nearScore() L2060–2071 — Returns a flat 8 on a substring hit, 0 otherwise. It only expands to your full home-term list when the Near box exactly equals the home label; type anything else and it matches that literal string alone. "Santa Monica" matches only text containing "santa monica"; "westside" and "the valley" match nothing.

Fix

Add a small alias map (westside → Santa Monica, Venice, Brentwood…; valley → Studio City, Sherman Oaks…) and grade the bonus: exact neighborhood 8, alias-group 5, same city 2.

F16
Year in Review ignores every undated entry, silently. Medium I 3 · E 2

reviewFor() L1305–1325 · L1308–1309 — The loop skips anything without a date. Three of nine entries never appear in any year's review, and nothing tells you they were excluded. Combined with F03, undated entries are second-class in every surface: sorted last, grouped under "Someday", and absent from reflection.

Fix

Once createdAt exists (F04), fall back to it for year bucketing and mark those entries as approximate. Add an "undated" count to the review header with a link that filters to them, so they can be fixed.

F17
"Away" is structurally undercounted — a blank city counts as home. Medium I 2 · E 1

isAway() L1236–1237 — if (!city) return false. Five of your nine entries have a blank or absent city, so they are all treated as home. Kings Road Cafe has neither city nor address. The Away tile in Year in Review is therefore a floor, not a count, and it is presented as a fact.

Fix

Return a third state — home / away / unknown — and render the tile as "3 away · 5 unknown" rather than implying certainty. Where an address exists but a city does not, parse the city from the address before giving up.

F18
Voice setting does not reach Discovery blurbs. Medium I 2 · E 2

LINES L1075–1102 vs catalog blurbs L529, L580, L613 — LINES is tone-keyed, but catalog blurb strings are frozen at authoring time. Switch the voice to Plain and Discovery still says "more full of shit than the middle film" and "weirder, hornier and meaner." The setting promises a global register it does not control.

Fix

Either scope the setting honestly — relabel it "Ledger voice" and note that Discovery copy is written when the item is indexed — or store blurb as {plain, dry, salty} and have Claude author all three. The first is one line; the second is the right answer if voice matters to you.

F19
Filters die on tab close and cannot be linked. Medium I 2 · E 2

readUi() L1165–1178 · stashUi() L1180 — UI state lives in sessionStorage and never touches the URL. Close the tab and your filters are gone; there is no way to save "want-to, food, near home" as a view or return to it tomorrow.

Fix

Mirror filter state into the URL hash so views are linkable and survive reload, and move the store to localStorage so the last view persists. Then a "Saved views" list is nearly free.

F20
Source attribution is invisible in the form that exists to review it. Medium I 2 · E 1

draftFrom() L2104–2120 · paint() L1779–1820 · detail L1737–1738 — Saving from Discovery attaches source and sourceUrl. They survive the save because collect() mutates rather than rebuilds. But the review form renders neither, so the one screen whose entire purpose is "check this before it enters your ledger" hides two of the fields being added — and there is no way to edit or clear them afterwards. The detail view does show them, which makes the omission look like a bug rather than a choice.

Fix

Render source as a read-only row in the form with a "Remove source" control, and show a "From Discovery · Wikipedia" chip at the top of the dialog so the provenance of the prefill is explicit.

F21
No offline handling; an edit made offline is lost on reload. Medium I 3 · E 3

persist() L2444–2468 — There is no navigator.onLine check and no write queue. Offline, the publish rejects and you get "Could not save — try again" while the edit exists only in memory. Reload and it is gone. On a phone — the most likely place to log a restaurant as you leave it — this is the realistic failure.

Fix

Mirror state to localStorage on every mutation as a crash/offline buffer, detect offline explicitly, hold the write and retry on reconnect. On load, if the buffer is newer than the published JSON, offer to restore rather than restoring silently.

F22
The "From Claude" suggestion slot has never been filled. Medium I 2 · E 1

recs: null L520 · openSuggest() L1994–2004 — state.recs is null, so the block never renders, leaving a bare "From your ledger" label distinguishing itself from a section that does not exist. The feature is built, documented in the how-to, and empty.

Fix

Either populate it — the schema is already specified at L2410 — or hide the "From your ledger" label when there is nothing to contrast it with. Do not ship a label for an absent counterpart.

F23
Five tools of wildly different weight are presented as five identical pills. Medium I 2 · E 2

toolsRow() L1539–1553 — Discover (a search product over an indexed catalog) sits in the same visual register as Order again (a list of four dish strings). Spin it, Suggest something and Order again all answer one question — "what now?" — from three different doors, and Year in review answers a different one entirely.

Fix

Group by intent: one primary Decide action opening a single sheet with Spin / Suggest / Order again as tabs; keep Discover as its own primary; demote Year in review next to the gear as reflection. Three doors, not five.

§ 04

Personalization and memory retrieval

These exploit data you already have, or data F01/F04 would add. Each one earns its place by answering a question the current ledger cannot.

Ratings turn a log into a memory

Once F01 lands, four things become possible that are impossible today: a "best of 2026" block in the review, "you rated three Middle Eastern places 4+" as a real recommendation reason, an "Order again" list ranked by rating instead of by whether you happened to fill a text field, and honest negative memory — the place you never need to try again.

Companion memory

observations() at L1380–1406 already computes days-since-last-outing per person and surfaces the stalest. That is the most human thing in the product and it is buried three clicks deep inside Suggest something. Trish appears on four of your nine entries. Promote it: a "You and Trish" view showing everything you did together, the streak, the gap, and what is on the shared want-to list.

Rediscovery beyond On This Day

The On This Day banner only fires on an exact month-day match in a prior year — with a ledger this young it will almost never appear. Add adjacent triggers that work now: a random buried entry ("you logged this eight months ago and never went back"), season matching ("last September you were doing this"), and the neighborhood you have not visited in longest.

Capture speed

J1 is eight interactions for a restaurant. Add a quick-capture path: title plus category only, everything else deferred, with the entry marked incomplete and surfaced later in a "finish these" list. The friction of full capture is what stops a ledger getting used.

§ 05

Discovery, recommendation and reflection

Make the catalog's limits legible

The index is 18 items and the page cannot grow it — a real architectural constraint, honestly explained in the ask-Claude panel. But that panel only appears on zero results. Show the index size and catalogAt date persistently in the Discovery header, and put "Ask Claude to index more" next to every result set, not only empty ones.

Give recommendations a quality signal

recommend() is a decent engine wired to weak inputs. With ratings it can say something true: "you rated two Villeneuve films 5 and this is the third." Add an explicit negative signal too — a way to dismiss a suggestion so it stops resurfacing, stored as dismissedAt rather than by deleting the entry.

Reflection beyond the calendar year

Year in Review is annual and calendar-bound, so for most of the year it reports a partial. Add a rolling "last 90 days" view and a lifetime view — total entries, longest streak, most-repeated place, the thing you have returned to most. Those read well at any moment; a year in review only reads well in December.

Close the loop on want-to

Nothing tracks whether Spin or Suggest ever led anywhere. Record which wishlist entries were surfaced and which later flipped to logged, then report it: "Spin has sent you somewhere 6 times." It makes the decide tools accountable and it is a genuinely satisfying number.

§ 06

Visual and interaction changes

The current surface is calm, well-spaced and consistent. It is also anonymous — it could be any well-made list app. These changes make it specific without redecorating.

  • Fix the contrast first (F07). Nothing else on this list matters if the metadata layer is unreadable. One token.
  • Let ratings carry visual weight. A five-dot glyph in the card's top-right, filled in the category color. It becomes the strongest scanning signal on the grid and it is the one thing only your ledger knows.
  • Differentiate the card by category. All four render identically today. A restaurant card should lead with cuisine and neighborhood; a film with year and director; a place with the map. Same frame, different emphasis — the summary array in CATS already declares the intent, the card just does not use it expressively.
  • Give the save indicator a real home (F08). Out of the tag bar, into a fixed corner toast with distinct in-flight, success and error forms.
  • Keyboard shortcuts. / focuses search, n opens new entry, Cmd/Ctrl+Enter saves the form, Esc closes. There are currently none, and this product is used repetitively enough to deserve them.
  • Density control. A comfortable/compact toggle. At 200+ entries the 11rem minimum card height means a lot of scrolling; a compact row view would make the archive browsable.
  • Retire the "Someday" group as a bottom bucket (F03). Undated wishlist items are intentions, not leftovers. They belong at the top of the want-to view, not in a basement.

§ 07

Privacy, persistence, portability, safety

What is actually true today

Entries live inside the artifact document, published to your Claude account. The artifact is private by default; the share link is currently pinned to an earlier version, so viewers see a pre-Discovery page rather than your live entries. Every save is a new version, so version history is a real backup — but it is only reachable by asking Claude, and nothing in the product says so.

On the runtime capabilities

artifact-save is already in use and working — this was the right call and needs no change. assets would let you attach a photo per entry, which is the single biggest emotional upgrade available to a memory ledger; the cost is document size and a real privacy decision, since photos travel with any share. The Claude runtime could write blurbs and suggestions on demand, but it would send your notes to a model on every call — for a private journal that is a meaningful change in posture and should be opt-in, per-action, never ambient. External APIs are impossible: the CSP blocks all outbound fetch, which is exactly why the Claude-fed catalog exists. Do not plan around them.

§ 11

Questions that must be answered first

Q1
Rating scale — five dots, or thumbs?

Five gives the review and recommender real resolution but invites fiddling over 3 vs 4. A binary "would repeat" is faster to capture and matches how you actually decide. F01 is specified as both; if you only want one, say which. My recommendation: five dots plus repeat, dots optional.

Q2
Is "Someday" a bucket you like, or an accident you tolerate?

F03 assumes undated entries are being lost at the bottom of the page. If you deliberately use "Someday" as a parking lot and are happy with it living at the end, the fix is only the sort label, not the grouping.

Q3
Trash retention — 30 days, or forever until purged?

Forever is safest and costs document size on a ledger you intend to keep for years. 30 days needs a purge job that runs on load, which is one more thing that can go wrong.

Q4
Does the voice setting need to control Discovery blurbs?

F18 has a one-line fix (relabel the setting) and a real fix (store three variants per blurb, and every future catalog item costs 3× the writing). Only worth it if switching to Plain and still seeing profanity actually bothers you.

Q5
What should the share link show?

It is currently pinned to a pre-Discovery version, so anyone you shared it with sees a stale page. Options: move the pin to current, keep it pinned deliberately as a curated snapshot, or unshare. This is the one item in the audit with an audience beyond you, and it needs a decision either way.

Q6
Photos — worth the privacy and size cost?

The assets capability would let entries carry an image, which is the biggest emotional upgrade available here. But photos travel with any share link and inflate the document. Not scheduled in the roadmap until you say yes.

§ 12

Six things that would make it genuinely yours

Everything above makes the ledger correct. This section is about making it specific — the difference between a well-built list app and something nobody else could have.

01 · Uses data you already have

The Trish View

Four of nine entries name her. observations() already computes the gap since you last did something with someone, then buries it. Surface a per-person page: everything you did together on a timeline, the current gap, the shared want-to list, and one line — "you and Trish have been to 3 restaurants and watched 4 things." That is a memory ledger doing the one thing a spreadsheet cannot.

02 · Needs F01 only

The Second-Chance list

Places you rated 3 — not bad enough to write off, not good enough to return to. That is the most useful and least-served list in anyone's life, and no product surfaces it because no product asks. Pair it with the opposite: the 5s you have not been back to in six months.

03 · Zero new data

Neighborhood pressure map

You have eleven home-base terms and every entry carries a city. Show which of your own neighborhoods you actually go to and which you have never logged once. "You have never eaten in Larchmont" is a genuinely useful provocation, and it comes free from data already in the file.

04 · Fixes the weakest recommendation

Make Spin argue for itself

The reel is charming and the result is a bare title. Give the landing a sentence built from the entry's own record — "you added this in March and have not moved on it," "this is the only Brazilian place on your list," "you rated the last two things Trish picked a 5." The animation is already the best interaction in the product; the payoff should not be the emptiest.

05 · Needs Q6

One photo per entry

Via the assets capability. A ledger of restaurants with no pictures of the food is a spreadsheet with opinions. This is the highest emotional return of anything in this document and the only item gated on a privacy call you have not made.

06 · Pure personality

Let the ledger keep score of you

Salty voice with real numbers behind it: "Nine entries. Two of them are movies you have not watched." "You have logged Trish four times and yourself alone five." A lifetime tile block that is honest rather than congratulatory. The voice system is already the most distinctive thing here — give it facts to work with instead of only empty states.
